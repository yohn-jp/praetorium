# T03 repository and operation store checkpoint

This checkpoint implements repository-keyed binding and instance resolution, desired-state mutation, durable operation claims/reports, and D1-backed runtime capacity reservations. D1 remains the desired-state authority; coordination objects can serialize calls but do not keep a second desired-state copy. Repository IDs are unique keys, while actor IDs are retained for audit only.

The D1 adapter uses expected-generation, binding-epoch, authorization-revision, runtime-epoch, policy, desired-revision, reservation, and observed-epoch predicates when applying desired-state changes. Idempotency records are committed with the operation. Operation claims are lease-epoch fenced and require a verified admitted build artifact for runtime starts and replacements; stop claims do not need an artifact. Checkpoints and reports carry monotonic sequences, and stale report observations roll back the terminal status update in the same batch.

Capacity admission requires a persisted complete snapshot within the configured freshness window and an exact capacity epoch. Reservations are fenced by the current operation lease and admitted revision resource requirements. Existing reservation rows must match the requested resources before attachment. Release requires the operation lease and a persisted writer-absence proof; stop and replacement have separate phase guards. The capacity query returns only active reservations and the actual persisted snapshot metadata.

The proposed schema is in `T03-schema.sql`; migration numbering and installation remain with the integration owner. It includes a transaction sentinel used to make D1 batch compare-and-set failures roll back preceding statements.

Leaf verification ran the proposed schema and application adapter against Node's SQLite implementation with transactional batches:

- `tsc -p packages/application/tsconfig.json`
- `tsc -p packages/persistence/tsconfig.json --noEmit`
- `vitest run packages/persistence/test/d1-platform-store.test.ts` — 5 tests passed

The tests cover competing first repository resolution, transfer/reinstall binding fences and webhook deduplication, concurrent idempotent desired-state requests, refusal to claim starts without an admitted artifact, incomplete-capacity refusal, mismatched reservation rollback, stale/idempotent operation reports, and writer-proof-fenced reservation release. This is a SQLite-backed leaf check, not Cloudflare D1 or Durable Object contention certification; the integrated Worker migration and DO tests remain required.
