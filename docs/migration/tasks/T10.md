# T10 — Management portal UI

## Scope

This unit adds a server-rendered repository management UI under `apps/gateway/src/ui`. It exports `createPortalHandler` for the Gateway router and renderer/type exports from `index.ts`. It uses native `Request` and `Response`; it adds no SPA framework or runtime browser dependency.

The handler serves `GET /`, `GET /repositories/:repositoryId`, and `POST /repositories/:repositoryId/actions`. The Gateway router owns mounting these routes and supplies the existing session, CSRF, and secure token adapters. The repository dashboard reads from a typed `PortalService` projection. No independent JSON API or persistence state is created by the UI.

## Service boundary

`PortalService` provides `listRepositories(actor)`, `getRepository(actor, repositoryId)`, and `execute(actor, repositoryId, command)`. Its view types carry GitHub App installation and repository permission state, current and desired image/module/resource state, approved releases, producer-resolved module previews, operator limits, entry state, and operation progress/errors.

`PortalActor.userId` must come from Gateway's authenticated session. The Gateway adapter supplies `authenticate`, the exact-origin/session-derived `verifyCsrf`, and a cryptographically secure `createToken`. The handler verifies CSRF before parsing or dispatching a form action. The `PortalService.execute` implementation must revalidate current GitHub repository permission for each request and enforce compare-and-set generation and idempotency for durable changes. `canConfigure` controls presentation only. The service must reject a crafted write from a read-only user even if the user sends a manually constructed request.

The typed commands cover preview, configuration/build request, same-configuration redeploy, operation retry, and entry. The UI does not calculate module dependencies or resource needs; preview values come from the producer and application service. It only labels dependencies as included modules that were not explicitly requested. Entry returns either an operation receipt while the service starts/waits for an instance or a one-use handoff. Handoff codes are rendered in a no-store POST form to the validated HTTPS instance origin, never in a URL.

## Behavior

- The repository list displays GitHub App installation status, current access, instance state, current/desired image digest, and latest operation state.
- Accessible repositories expose an Open action directly in the list, including repositories without an instance binding. The entry service resolves the binding before it starts, waits for, or hands off to the application; a dashboard link appears only once an instance ID exists.
- A dashboard displays the current and desired release/image, requested modules, included modules/dependencies, resource allocation, producer-backed preview, operator resource limits, and operation progress or errors.
- Enter submits through the application boundary. Starting or stopped instances can return an operation receipt; failed/blocked states expose retry only when the current view marks the operation retryable. The handoff page submits the one-use code to `/_platform/handoff`.
- Maintain/admin controls select an already approved base release, producer-declared modules, and an approved resource profile. Unsupported combinations and resolver errors remain visible. Read controls omit configuration/redeploy/retry buttons, while the application service remains responsible for rejecting forged or stale writes.
- Redeploy always calls the lifecycle service for the current desired configuration. When current and desired image digests match, the page states that the operation still creates a new runtime epoch.
- Active operations refresh at most five times with increasing delays (1, 2, 4, 8, and 16 seconds), then stop and leave an explicit manual refresh link. Errors do not keep polling or hide the failure.
- HTML output is escaped, is `no-store`, and uses a restrictive CSP. The handoff CSP limits form submission to the validated instance origin.

## Verification and integration status

`portal.test.ts` covers renderer escaping, installation/access display, accessible unbound-repository entry, current/desired state and resources, dependency preview, same-image redeploy messaging, service-denied read-only mutations, CSRF rejection before service dispatch, service errors/build failures, bounded polling, and handoff POST/CSP handling. These are unit/handler tests with service fixtures; they do not certify a deployed or integrated application service.

The Gateway router/session integration is owned by the Gateway entry task. T06/T09 must provide the actual build and lifecycle services. Real-browser acceptance remains an integration gate: verify read-only controls against the live authorization boundary, configuration preview, cache reuse, build-failure preservation, same-image redeploy, direct-origin wake, and cookie/handoff behavior after those services and routes are wired. No production or Actions flow is introduced here.

## Operation retry integration

The existing portal retry form now calls the real Control Plane retry endpoint. The Gateway rechecks current maintain/admin authority, derives the actor from its authenticated session, verifies the operation belongs to the bound instance and forwards the recorded generation plus current binding/authorization revisions. Only failed or blocked operations on the current generation are rendered retryable. An old-generation retry can succeed only by replaying the Control Plane's existing durable idempotency receipt; a fresh stale request is rejected. The same CSRF-validated UI command path is retained. Focused tests cover authorization, request scoping, stale status and idempotent replay; real GitHub/browser/producer retry acceptance remains a T14 gate.
