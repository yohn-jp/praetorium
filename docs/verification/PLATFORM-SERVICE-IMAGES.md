# Platform service image verification

The three Platform service images were built from real Praetorium workspace packages and canonical Dockerfiles, then verified against the local OCI registry. This verifies package deployment and a bounded set of runtime paths. It is not a producer composition acceptance or a production deployment.

## Source and immutable build inputs

The image source cut was clean Praetorium `main` commit `431dbe1c7c86251894efea3de2cf0ec94499ca10`, tree `17e0acdff802c39127611842cc53dc31e40a70f4`. The service Dockerfile Git blob is `1e27cfc1c12989e82554bde46fc993f8a966ab30`; the Build Worker Dockerfile blob is `c7ef0bc81f2f68d76b2be05125a6ef481fcbcb3d`. The Dockerfile source used an immutable official Node base for both build and runtime stages: `docker.io/library/node@sha256:a5f4366e834695d5f363b920c104953a535d3a9864d1bdf74566a0ebe01daee5`. An actual BuildKit `RUN node --version` returned `v24.22.0`.

The Build Worker copied `buildctl` from official BuildKit v0.30.0 image `docker.io/moby/buildkit@sha256:c1d0a1bc930a427f99f72220d1b263d6986d4592b21507fbc7f8bf7ecdaed004` (linux/amd64 child of index `sha256:d76eb1caecac5733ef7553c1e90a1b21f1bb218cd1142d3553de0747b4a14ba9`). Its source path was `/usr/bin/buildctl`. A private, mode-0600 component test input read `buildWorker.buildctlPath=/usr/local/bin/buildctl` from a test-only inventory and passed the same value as the Dockerfile build argument. The input file SHA-256 was `9a8f8fe369b65a181a3e0530508c0a302b95f996c6e9aa0afd727faa48afc07d`; the checked-in disposable inventory was left unchanged with this optional path unset. This single-field input is not the full deployment baseline.

The first real package build confirmed that `pnpm deploy --prod` fails with `ERR_PNPM_DEPLOY_NONINJECTED_WORKSPACE` when workspace package injection is disabled. The canonical service Dockerfile was corrected to use `pnpm deploy --prod --legacy`; all three actual package builds then succeeded. Production dependencies are materialized at image build time. The final images do not run `npm install` at startup.

For the Provisioner, a private disposable test credential was mounted at the configured secret path. The Instance Access readiness check used a private synthetic Gateway token; its saved inspect record confirms `network=none`. The Build Worker check below was an image diagnostic, not a service-entrypoint startup check.

## Disposable BuildKit launcher recheck

This evidence supersedes the earlier `LOCAL-ENVIRONMENT.json` `newuidmap` blocker only for the launcher and local Node base probe described here; that file remains an accurate historical record of its earlier source and attempt.

A fresh full lifecycle was run with worker source `fe824863a08ffa871dcd88cfb66413565cfa52e6` (tree `16318f0fe4c8124a7edefa3a75a69e66f17d4ecf`) on `worker/service-image-acceptance-20261017`. The exact tested launcher blob SHA-256 was `2d78ab667c41f823b201b6bdc0716ed5b4ed3b3ff26582457a673896e45193bd`. It created root `/tmp/praetorium-owned-Q5Vhro`, initialized private rootless Podman 5.8.8, started an anonymous loopback registry, and completed an uncached BuildKit scratch-image round trip. It then built `FROM docker.io/library/node@sha256:a5f4366e834695d5f363b920c104953a535d3a9864d1bdf74566a0ebe01daee5; RUN node --version`, which printed `v24.22.0`. The output manifest was `sha256:ed6bc299eac2145b1d05831f45bfcf5d54aee3fdb83f9119c8a07adb1522fa2d`, config `sha256:735ce116a4e811889cf2528dc279506546c34bfcf1939352c936df342d7ba575`; manifest header, metadata digest, config, and all layer descriptors were verified.

The launcher recorded UID map `0:1000:1,1:100000:65536`, GID map `0:100:1,1:100000:65536`, and kernel overflow UID/GID `65534/65534`. Cleanup using that same source commit exited 0 and the exact root was absent. Cleanup revalidated the marker, maps, overflow settings, mount points, filesystem device and mapped ownership inside the same private user/mount namespace before removing the tree there. It conservatively rejects any entry reported with the kernel overflow UID/GID; that also rejects a legitimate mapped `65534` owner rather than risk deleting an ambiguously mapped tree.

The follow-up source changes `839d8bb8b2a64698f7c2c5e9f243ce76588493ac` and `f12d590c01bf136e3a08cffeb10581c1f11ba78e` removed an unreachable legacy cleanup branch, corrected the plan's read-only kernel-probe wording, and formatted the launcher. They do not change the tested v2 mapped cleanup path. The final source passed Node syntax, ESLint, Prettier, `--plan` assertion, and `git diff --check`; a separate read-only review of `f12d590` closed without findings.

The product image builder root `/tmp/praetorium-owned-CU2A6s` was retained while image digests were independently read and the Build Worker archive was loaded by the separate Kind owner. It contains only this task's disposable loopback registry and local BuildKit/Podman stores. Stop it through its ownership-checked launcher after the separate Kubernetes owner confirms it no longer needs the exported artifact; do not use this registry as producer acceptance.

## Acceptance limits

These results cover three actual Praetorium image builds, registry content-address checks, the listed restricted service process paths, and a generic local BuildKit/registry substrate. No Scriptorium composition artifact, catalog receipt, assignment, producer credential, or S01-S05 acceptance was consumed. Build Service/T06, producer recovery, stable rollout, and the projected-secret Kubernetes Pod probe are not proved by this evidence. This unit pushed no public image/package and triggered no CI or Actions; a separate read-only audit observed existing producer release runs without starting them. No production cluster or infrastructure was changed.
