# Praetorium — Design and UX contract

## 1. この文書の位置付け

本書は、Praetoriumが利用者と運営者に保証する体験の正本である。実装済み機能や本番受入の報告ではない。MUST／禁止は受入条件、SHOULDは例外理由と代替の証拠を要する設計原則とする。画面画像、過去のモック、特定製品の外観は仕様ではない。

最新の明示的なオーナー指示と受入済み製品契約を優先する。本書は表示・操作・情報設計を定め、認可、データの正本、公開Origin、Writer安全性を変更しない。矛盾は見た目を優先して解消せず、該当契約と実装差分を特定する。

関連正本は [Admin Plane](../architecture/ADMINISTRATION.md)、[Management Plane](../architecture/MANAGEMENT-PLANE.md)、[Application Origins](../architecture/APPLICATION-ORIGINS.md)。過去のOperator Console計画の色・固定ナビゲーション・画面割りは本書で置き換え可能とするが、診断、認可、復旧の契約は維持する。

Praetoriumの画面構造は破壊的に再設計してよい。ただし、URLの公開契約、既存データ、権限、サービス責務を破壊してよいという意味ではない。既存のTypeScript、Workers、プロバイダー境界を使い、UI更新を理由に基盤を置換しない。

## 2. 製品として実現すること

**利用者は、正しいリポジトリの作業環境へ入り、必要な構成変更を理解して行い、中断後も作業へ戻れる。運営者は、同じ基盤の問題をブラウザから診断し、根拠のある安全な操作へ進める。**

PraetoriumはGitHubの権限に基づく登録済みアプリケーションの実行基盤である。Scriptoriumは最初の利用アプリケーションであり、任意Dockerfileを投入する汎用PaaSでも、公開Webサイトのデプロイ管理製品でもない。

| 利用主体 | 最初に答える問い | 主役になる対象 | 通常は後景に置く情報 |
| --- | --- | --- | --- |
| 作業へ戻る利用者 | このリポジトリを今開けるか | リポジトリ、選択したアプリ、実際の利用可否、入る操作 | VM名、内部ID、イメージdigest、全体メトリクス |
| 構成を変更する利用者 | 何が変わり、今の作業に何が起きるか | 現在／要求構成、承認済みRelease、モジュール、リソース、適用結果 | 通常のビルド内部ログ |
| 運営者 | 何が利用を妨げ、何をすればよいか | 未解決の阻害要因、影響範囲、処理段階、根拠、許可された操作 | 解消済み履歴、正常系の大量の数値 |

一般利用者のGatewayと独立Admin Workerの入口・認可を分離する。GitHubリポジトリ管理権限はPlatform operator権限ではない。管理機能を通常画面の隠しタブに混在させてこの境界を曖昧にしない。

## 3. 情報の同一性と読み順

### 対象モデル

- 利用者向けの安定した対象は `(app_identity, numeric repository_id)` の論理Binding。リポジトリの表示名や物理Runtimeが変わっても別の作業対象として扱わない。
- 実行中Runtime、要求構成、承認済みRelease、Composition Build、Operation、Attemptは別の対象。共通の「デプロイ成功」へ丸めない。
- 表示名と正確な識別子を併用する。通常は人が読める名称を先にし、同名対象の識別と調査時には完全なID／digestを確認・コピーできる。
- 登録済みアプリだけを選べる。単一アプリの場合に不要な選択を強制せず、将来製品のカードや無効なインストールボタンを追加しない。

### 情報アーキテクチャ

利用者側は「リポジトリを見つける → 作業環境を開く／必要な構成を決める → 実行結果を確認する」。運営者側は「影響と要対応事項 → 対象Release／Work／VM／Service → 根拠と次の操作」。画面名、タブ数、サイドバーの形は固定しない。

各主要画面は、第一に**対象と現在の事実**、第二に**理由と次の安全な行動**、第三に**詳細根拠と履歴**を読める構成にする。利用者に複数画面の断片を記憶させて状態を推測させない。新規利用の導線は必要だが、既存環境を開くために設定ウィザードを繰り返させない。

## 4. 利用者向け契約

### P-01 — 自分が入れる対象を発見できる

認証後、アクセス可能なリポジトリとアプリ、その状態、権限に応じた操作を示す。未接続、GitHub App未導入／停止、対象外リポジトリ、権限不足、検索該当なし、取得失敗を「何もありません」に統合しない。

原因を取得できない場合は不明とする。権限のないリポジトリ名を説明のために漏らさない。修正主体が本人かリポジトリ管理者かPlatform operatorかを区別し、利用可能な正規導線を示す。問い合わせ先機能がないのに存在するように案内しない。

### P-02 — 作業を開く過程が途切れない

起動済みなら作業へ、停止中なら既存契約に従うWakeと進捗へ、未構成なら必要な設定へ進める。ログイン／handoff後も許可された元の対象に戻る。認証依存先の障害を権限拒否に偽装しない。

公開アプリのブックマークはRuntime置換をまたいで同じ論理対象へ解決する。無限リダイレクトや無限スピナーで終わらず、状態確認の継続方法と戻り先を提供する。接続失敗時に未確認の書き込みを自動再送しない。内部Runtime URLや認証コードを公開リンクとして配布しない。

### P-03 — 構成を理解して確定できる

現在と要求中の構成、stable追従とpinned、選択したモジュールと必須依存、リソース割当を区別する。モジュールはIDだけでなく利用者が選択理由を理解できる名称・説明を示す。すべての任意モジュールが必須であるように見せない。

Previewは変更しない確認であり、確定はビルド／適用を起動する操作だと明示する。選択内容が無効化された場合も消さずに理由を示す。変更差分と影響を確認してから正規APIへ一度の意図として送信する。revision／generation／idempotencyの検査をUI都合で省略しない。

承認済みReleaseなし、Resource Profileなし、取得中、取得失敗、権限不足は別々に表示する。「承認後に選択してください」の一文で行き止まりにしない。一般利用者には待機理由と担当主体、operatorには権限内の該当管理画面を示す。必要なデータがAPIにない場合は最小の正規read modelの不足として扱い、成功値を補造しない。

### P-04 — 現在の稼働と進行中の変更を混同しない

| 表示する事実 | 混同してはいけないもの |
| --- | --- |
| 現在のRuntime状態 | 要求構成の保存、ビルド成功、ブラウザ接続成功 |
| 要求した構成と対象世代 | 現在提供中の構成 |
| OperationとAttemptの状態 | HTTP要求受付、UIアニメーションの完了 |
| 観測の鮮度・取得結果 | リソース自体の稼働／停止 |
| Source／Release／Stableの状態 | GitHubにtagがあること、最も新しいversionであること |

既存Runtimeが利用可能なまま変更が失敗した場合、利用可能性を失敗表示で覆い隠さない。逆に過去のReadyを新しい観測として緑表示しない。未取得・古い観測・取得不能には、その意味と確認できた範囲を添える。

### P-05 — 待機中も移動し、結果へ戻れる

長時間処理は操作受付、実行中、完了、失敗、結果不明を区別し、対象IDと確認可能な段階を保持する。他画面への移動、戻る、再読み込みでも同じ処理を参照でき、再送フォームから重複処理を作らない。

進捗率や残時間は実測できる根拠がある場合だけ示す。処理状態を取得できないことは、その処理が失敗した証拠ではない。無関係な安全な操作まで全画面ロックしない。状態更新は表示対象に必要な範囲に限定し、非表示時の常時ポーリングや既知の同一データの再取得を増やさない。

### P-06 — 変更と復旧の影響が予測できる

停止、同一イメージ再作成、構成変更、再試行について、対象・影響・利用不能の可能性・保存上の条件を操作直前に示す。確認は重大な変更に比例させ、閲覧まで毎回確認させない。

quiesce、未公開Checkpoint、旧Writer不在、世代フェンス、rollback互換性の正規判定を守る。サーバーが許可しないRetry／Cancel／Rollbackを見せかけのボタンで提供しない。結果不明の操作は既存IDで確認してから再試行する。再試行のための手動D1更新や通常のSSH作業をユーザーに要求しない。

## 5. 運営者向け契約

### P-07 — Releaseを利用可能にする経路を追える

承認対象のpublished version tag、Sourceの不変同一性、Source Build、検証・Admission、Canary、Stableの関係と、どこで止まっているかを辿れる。利用者用の選択肢に現れない理由もこの経路から確認できる。

通常のRelease選択は正規のversion-tagポリシーに合致する候補に絞る。branchや無関係なtagをReleaseとして並べない。履歴調査に必要な識別子は失わない。Stableは正本のchannel pointerで判断し、versionの大小や一段階の成功から推測しない。

### P-08 — 障害をブラウザから診断し、安全に対応できる

失敗対象から、処理段階、Attempt、canonical error code、分かっている原因、許可された復旧操作、関連する根拠へ到達できる。不明な原因を推定で断定しない。ログが未保存・期限切れ・取得不能ならその違いを明示する。

運用情報は必要な範囲に限定・ページ分割し、秘密情報と作業原稿を除去する。Retry可否、revision、idempotencyは既存の正本に従う。復旧操作後も以前の失敗Attemptを履歴として残し、新しい試行と同一視しない。

### P-09 — 今対応すべき問題と過去の失敗が分かれる

現在の要対応一覧は、単に過去にfailedだった全レコードの一覧ではない。同一対象の後続成功や置換によって解消・supersededになった問題は、正本の条件と根拠に基づき要対応から外し、履歴から調査できるようにする。

新versionの存在だけで別Source、別Runtime、pinned環境、継続中の基盤障害を解消扱いにしない。履歴のfailedをsuccessに書き換えない。「未確認」「対応不要になった履歴」「現在の阻害」を区別する。UI独自の第二のincident台帳は作らない。

### P-10 — 基盤のどこまで確認できているか分かる

Management／Runtime／Builder、Service、Workの関係を辿り、状態、観測元、最終観測、対象作業への影響を確認できる。観測不能を健康・障害・ゼロ使用量に置き換えない。部分的な取得失敗で利用可能な独立情報まで消さない。

Observerはread-onlyであり、見える資源が操作できる資源とは限らない。存在しない時系列を描いたCPUグラフ、推定稼働率、無根拠な全体Healthy、任意Shell、汎用Kubernetes管理機能を追加しない。

## 6. 表示と操作の品質契約

### P-11 — 状態更新が操作場所を動かさない

通知や更新でヘッダー高、実行ボタン、選択行、入力欄が予期せず移動しない。入力中の構成、フィルター、選択対象、スクロールを保つ。通常の受付・成功は非モーダル、対処が必要な問題はその場に残す。トーストを読まなければ失敗が分からない設計にしない。[R2][R3][R5]

画面遷移時は新しい主内容を認識できるfocus管理を行うが、背景更新ではfocusを奪わない。処理結果は必要な差分だけ通知し、ポーリングのたびに読み上げない。再読み込みで失われる純粋なUI状態とサーバーで継続する作業状態を混同しない。

### P-12 — 同じ契約を異なる操作環境で満たす

Desktopは比較、一覧、詳細の同時参照、キーボードを活かす。Mobileは一つの対象、根拠、次の行動へ順に進める構成とする。表の縮小、文字の極小化、hoverだけの説明、隠された横スクロールを主要導線にしない。

画面幅だけでDesktop／Mobileの選択を上書きせず、明示したmodeと対象・フィルターを保つ。狭いDesktopにも破綻しないレイアウトを用意する。タッチ端末に必要な操作を「モバイルだから」で削除せず、適切な別導線へ置く。safe area、ソフトキーボード、戻る操作、拡大表示を扱う。

## 7. 視覚デザインの判断基準

**対象の利用可否と次の安全な行動が、装飾や基盤の複雑さより先に目に入る。** これをPraetoriumのデザイン命題とする。

- 構図はタスクから決める。利用者には作業対象、operatorには未解決の阻害と根拠を大きく扱い、均等なKPIカードで第一画面を埋めない。
- 名称、状態、理由、行動を近接させる。同じ種類の行は同じ位置で比較でき、例外だけが意味のある強調を持つ。
- 文字階層、余白、境界、状態色、focusを少数の意味的tokenで統一する。ブランド色と成功／警告／失敗の意味を混ぜない。
- 日本語・英数字・長いリポジトリ名・完全digestで評価する。重要な対象や行動を省略だけで隠さず、技術情報は展開可能にする。
- 動きは展開、移動、受付など実際の変化を説明する場合に限る。reduced motionでも同じ情報を伝え、アニメーションを実行成功の根拠にしない。
- 配色、ライト／ダークの初期値、フォント、角丸、パネル数は実装側の裁量。別製品の画面模倣、ブランド更新、全コンポーネントライブラリ導入を受入条件にしない。

完成した代表画面を原寸と縮小、色ありとグレースケールで確認する。最初に見える情報が主要判断と一致しなければ、装飾ではなく構図を修正する。美しさを自称の点数やスクリーンショットの枚数で認定しない。

## 8. アクセシビリティと応答性

WCAG 2.2の適用可能なA／AAを基準に、構造・ラベル・コントラスト・キーボード・focus・エラー通知を検証する。通常文字4.5:1、大きな文字3:1、必要な非テキスト要素3:1、色以外の状態識別、200%文字拡大、320 CSS px相当でのreflowを扱う。表など本質的な二次元表現の例外は理由を明示する。[R1]

タッチの主要操作は44×44 CSS px以上を製品の設計目標とする。WCAG AAの24×24と許容例外を44pxの義務と誤記しない。dragにはクリック／キーボード代替を、modalには適切な初期focus・閉じる手段・復帰先を用意する。固定領域がfocus中の操作を覆わない。[R6][R7]

ローカルな操作反応をネットワーク完了まで待たせない。INPのp75 200ms以下とCLSのp75 0.1以下を外部の品質目安として参照するが、デプロイ完了時間や単発のPlaywright実行時間と混同しない。フィールドデータがない場合は未計測とする。対象操作の前後で応答・位置安定・通信量を同条件で測り、処理短縮のために認可を省略しない。[R4][R5]

## 9. 受入シナリオ

以下はテスト義務であり、実行済みチェックリストではない。操作前、受付、遅延、結果、復帰を実ブラウザで確かめ、該当する契約IDへ証拠を対応付ける。

| シナリオ | 条件・操作 | 必須の観測結果 | 契約 |
| --- | --- | --- | --- |
| P-A01 | 未認証から許可された対象へログイン／復帰。権限拒否と認証依存障害も試す | 元の対象に到達、無限遷移なし、拒否と取得不能が別、秘密や他人の対象を露出しない | P-01,02 |
| P-A02 | 未接続、App停止、権限不足、検索0件、一覧取得失敗 | 原因・修正主体・可能な次の行動が異なる。空配列への握り潰しなし | P-01 |
| P-A03 | Releaseなし／Profileなし／片側取得失敗、一般利用者とoperator | 個別の阻害と適切な導線。無効な確定と架空の選択肢なし | P-03,07 |
| P-A04 | module依存、stable／pinned、構成変更、Preview、二重押下、stale generation | Previewは非変更、差分を理解できる、正規契約に従い重複／古い更新を拒否、選択保持 | P-03,06 |
| P-A05 | 既存Readyを残した構成ビルドの失敗、状態読出し中断、再読み込み | current／desired／operation／unknownが分離。同じOperationへ戻る | P-04,05 |
| P-A06 | 停止中の公開URL、起動待機、handoff失敗、Runtime置換後の再訪 | 安定した論理対象への復帰、無限待機・write自動再送なし | P-02,05,06 |
| P-A07 | 停止／同一イメージ再作成を安全ゲートが拒否 | 影響と拒否理由を表示。Writer保護を迂回せず、無関係な閲覧は可能 | P-06 |
| P-A08 | Source失敗からAttempt根拠、許可Retry、Admission／Canary／Stable確認 | 段階と結果が一致、古いAttempt保持、受付を成功扱いしない | P-07,08 |
| P-A09 | 後続成功で置換済みの失敗と、独立して継続中の障害を同時表示 | 前者は履歴、後者は要対応。範囲を超えた一括解消なし | P-09 |
| P-A10 | Observer部分障害、古い観測、証拠未保存／期限切れ | Unknown／stale／missingを区別し、取得できた情報は残す | P-08,10 |
| P-A11 | 長い名称、通知更新中の入力、keyboard、touch、mode切替、戻る | 主要操作・文脈・focus維持、水平はみ出し／突然の位置移動なし | P-11,12 |
| P-A12 | 一般利用者、operator、失効session、CSRF違反で直接APIと画面へアクセス | UI非表示だけでなく正規境界で拒否。ログ／traceに秘密なし | P-01,06,08 |

検証幅はDesktop 1440／1920、Mobile 320／375／390／430 CSS pxとし、狭いDesktop、拡大、長文、空／不明／失敗も含める。モードは幅とは別に指定する。

合格は **視覚・情報階層／操作・accessibility／正本・安全性** を別々に判定する。fixtureでのUI分岐確認、正規サービスを通る統合確認、本番／実機確認は別の証拠である。実行できない項目はBLOCKEDまたはNOT_CHECKED。Playwrightのemulationは実機のIMEやOS挙動を証明せず、自動accessibility検査も全適合を証明しない。[R8][R9]

証拠には対象revision、環境、fixture、操作、期待／実際、結果、画像・traceの所在を残す。原稿・OAuth・cookie・認証済みstorage stateを公開artifactに入れない。実行記録はPR／検証artifactへ置き、本書へ時点の結果を追記しない。

## 10. 実装上の責務と非目標

GatewayのPortal表示・操作は `apps/gateway/src/ui` と既存Portal service、管理側は `apps/admin/src/admin` と既存view model／service境界を利用する。Control Planeの状態・権限をUIで再実装しない。必要なデータ不足は正規境界内の最小の契約拡張として扱い、独立した状態DBや認証系を増やさない。

本書は、機能削減、認可緩和、任意アプリmarketplace、billing、追加VM、汎用監視基盤、リモートShell、保存方式変更、CIゲート省略、本番デプロイを許可しない。新しい画面のためだけの機能は作らず、既存対象を必要な情報と操作で結ぶ。

## 11. 調査根拠と採用範囲

外部資料は設計判断の根拠であり、製品要件やライブラリ導入指示ではない。引用元の製品の画面・CSSを複製しない。

| ID | 一次資料 | この製品への適用と限界 |
| --- | --- | --- |
| R1 | [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/) | 適用可能なA／AAの検証基準。自動ツールだけで適合を宣言しない |
| R2 | [IBM Carbon: Empty states](https://carbondesignsystem.com/patterns/empty-states-pattern/) | 空の理由と次の行動を対象内で説明。Carbon部品の導入ではない |
| R3 | [IBM Carbon: Notifications](https://carbondesignsystem.com/patterns/notification-pattern/) | 通常通知と判断が必要な問題の介入度を分ける。通知センター新設の要求ではない |
| R4 | [web.dev: INP](https://web.dev/articles/inp) | 入力への反応と非同期完了時間を分離。ラボ測定をフィールドp75と呼ばない |
| R5 | [web.dev: CLS](https://web.dev/articles/cls) | 予期しない移動を抑える。CLSだけでfocusや操作位置の安定を認定しない |
| R6 | [WAI: Target size minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) | AAの最小条件と製品の大きいtouch目標を区別 |
| R7 | [WAI APG: Modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) | modalのfocus／閉じる／復帰。通常の進捗をmodal化する要求ではない |
| R8 | [Playwright: Emulation](https://playwright.dev/docs/emulation) | viewport・touch条件の再現範囲と実機確認の区別 |
| R9 | [Playwright: Accessibility testing](https://playwright.dev/docs/accessibility-testing) | 自動検査と操作・支援技術による評価を組み合わせる |
| R10 | [WAI: Status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) | focusを奪わない状態通知。更新の連続読み上げは避ける |
