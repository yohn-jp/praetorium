# Installing NixOS on Proxmox VMs for Praetorium

Only the first operating-system installation is manual. Praetorium does **not** alter the Proxmox host, partition an existing device or run `nixos-install` on an unknown disk. This document describes a repeatable operator-reviewed first boot that leads to the automated [deployment](REPRODUCIBLE-DEPLOYMENT.md).

1. In Proxmox create two **new Linux VMs** (`praetorium-runtime`, `praetorium-build`). Boot each from a **verified official NixOS 26.05 x86_64 ISO**. Record ISO URL/checksum, chosen UEFI/BIOS mode, VirtIO storage identifier and VM resource allocation in an operator-private deployment log. Set NIC to the existing controlled management bridge; do not expose SSH or K3s API directly to the internet.
2. Give each guest an OS disk and stable network/management address. The Build VM additionally needs a **dedicated disk for rootless BuildKit's XFS cache**; choose its by-id device only after inspecting `lsblk -o NAME,SIZE,MODEL,SERIAL,FSTYPE`. Its formatting is a separately approved destructive step, not automatic and not on the OS disk.
3. Follow the official NixOS install process for the selected boot mode (graphical installer or the CLI): make the intended partitions and filesystems **on the identified new OS disk**, mount them at `/mnt`, run `nixos-generate-config --root /mnt`, verify bootloader/network/user settings, run `nixos-install` and reboot. Save `/etc/nixos/configuration.nix` and `hardware-configuration.nix` from the installed guest. This project deliberately does not embed a guessed `parted`/`mkfs` command.
4. Ensure the guest reaches GitHub/NixOS package sources over outbound HTTPS and has `nix-command`/`flakes` enabled in its Nix settings. Add an operator public SSH key to the installed account; disable password login after access is confirmed. Use the guest console on first boot until networking and recovery access are verified.
5. From the guest, clone `yohn-jp/praetorium` at an immutable reviewed commit into `/opt/praetorium`. Prepare `/root/praetorium-runtime.nix` or `/root/praetorium-build.nix` from the corresponding example, with **real** cluster identity, management CIDRs, operator public SSH keys and resource/secret-path declarations. Store secret bytes outside Git and Nix source.
6. Run `sudo bash /opt/praetorium/scripts/bootstrap-linux.sh runtime /root/praetorium-runtime.nix --check` (or `build`) and review the evaluated NixOS system. Then repeat with `--apply`. This creates/updates an explicitly marked `/etc/nixos/flake.nix`, preserves the installer-provided baseline and pins the imported Praetorium role/OS package graph. It **refuses to overwrite an unrelated existing flake**. Reboot and verify K3s or rootless BuildKit service health.

The NixOS role's default firewall has no public runtime ingress. It restricts SSH and the Kubernetes API to the exact administrator CIDRs supplied by the operator. If the approved VPS/tunnel forwards public HTTPS to Traefik, explicitly enable and constrain the necessary port through the reviewed role input. K3s uses the cluster identity label for later deployment ownership validation.

The runtime guest supplies a restricted copy of the K3s administrative kubeconfig for the automation host. The build guest supplies the mTLS BuildKit endpoint only to the allowlisted Build Worker network. Do not copy the Kubernetes control credential or BuildKit signing key into a public Git checkout.

After this one-time installation, platform application updates are handled by [the one-command deployment](REPRODUCIBLE-DEPLOYMENT.md). Normal updates require no further Proxmox console interaction.
