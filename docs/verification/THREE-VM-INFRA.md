## Writer and cutover gates

The current Runtime systemd unit is `/etc/systemd/system/k3s.service`, active with `KillMode=process`, `Delegate=yes`, `Restart=always`, and no explicit `ExecStop`. K3s documents that stopping the service leaves Pod containers running, while `k3s-killall.sh` stops them and resets containerd ([K3s stopping](https://docs.k3s.io/upgrades/killall)). The K3s docs do not promise that an in-place Server→Agent role conversion preserves the same Pod UID or guarantees that a new Agent adopts the old kubelet/container state. The live Pod UID therefore cannot be assumed to persist across conversion; that behavior is `NOT_CHECKED` and needs a same-version disposable conversion rehearsal. Do not use `k3s-killall.sh` or uninstall as a shortcut while workspace recovery is incomplete.

The Lifecycle owner reported that the authenticated producer status/quiesce request returned HTTP 409 because the active operation and generation did not match. No checkpoint or quiesce receipt exists, and writer absence is unproven. The old Pod remained Ready at the last direct read-only check. Therefore all Runtime gates remain false: `writerQuiesced`, `writerAbsent`, `runtimeServerRetired`, and `runtimeAgentTransitionAllowed`. A Ready Management API or restored cluster does not establish old-writer absence.

Do not start the restored Management server as a competing production writer, alter the Runtime role, or restart/delete the tenant Pod until all of the following are true:

1. Resolve the active lifecycle operation with the producer owner, obtain authenticated status, a successful quiesce receipt, and any required checkpoint receipt.
2. Copy the complete Runtime `emptyDir` workspace and all pending producer data to protected storage, restore it in a disposable location, and verify the unpushed commit and exact unpublished work. The current Git bundle alone does not meet this gate.
3. Prove the original writer is absent and record the evidence against the exact Runtime epoch and generation. Keep the independent D1/epoch/CAS fence authoritative.
4. Let the concurrent TLS/Helm changes settle, create a fresh snapshot and credential bundle, and rerun the isolated restore/resource comparison.
5. Rehearse the full same-version Management Server restore and Runtime Server→Agent transition in disposable hosts. Verify API/CA/cluster identity, the Runtime Node identity, Pod UID and container continuity or a safe replacement path, the PVC, ingress/TLS, and no second writer. K3s' service-stop note alone is not this proof.
6. Obtain explicit owner go-ahead for production cutover after the evidence is reviewed.

Only then should a single-writer cutover be scheduled: fence and quiesce the old writer first; ensure Runtime Server is no longer an etcd writer before Management becomes the only Server; restore the verified snapshot and token on Management using K3s' documented embedded-etcd procedure; validate the restored API and state; then apply only the rehearsed Runtime Agent transition and the role label/Management taint. Keep the old Runtime datastore, token, certificates, and systemd configuration intact until integrated acceptance. The exact Server→Agent conversion commands remain intentionally unspecified here because the disposable transition rehearsal has not yet established a safe, data-preserving procedure for this live node.

For rollback before Management accepts writes, stop and verify Management K3s is inactive, then restart the untouched Runtime Server and verify the original cluster identity/API. Never run both separate single-member embedded-etcd datastores as active writers. Once Management has accepted writes, do not restart the stale Runtime datastore: snapshot Management and its matching token/credentials first, then recover a single Server from that state.

K3s references: [embedded-etcd backup and restore](https://docs.k3s.io/datastore/backup-restore), [etcd snapshot restore procedure](https://docs.k3s.io/cli/etcd-snapshot), and [service stop behavior](https://docs.k3s.io/upgrades/killall). K3s requires the matching server token when restoring because it encrypts datastore bootstrap data. The rehearsal demonstrated the full artifact is usable with that token; it did not authorize migration.

For an Agent, K3s documents setting `K3S_URL` and the matching agent token; setting `K3S_URL` makes its installer configure the node as an Agent ([K3s quick start](https://docs.k3s.io/quick-start)). That is an install contract, not a promise that converting this existing Server preserves its Pod UID or live container state. Keep the exact Runtime conversion command gated on the disposable same-version rehearsal above; do not run the Server uninstall script because K3s documents that uninstall deletes local cluster data, configuration, and Pod-created local storage ([K3s uninstall](https://docs.k3s.io/installation/uninstall)).
