## Fixed ownership and interfaces

- Sol alone owns shared package manifests, exported contracts/schemas, inventory templates/schema, D1 migration sequence and final composition wiring. Agents propose exact changes to those files. Existing migration names are not rewritten: the duplicate historical `0004_*` prefixes must be handled by explicit complete ordering/preflight, with new additive migration after `0006`.
- A owns `source-producer-builder.ts`, `source-producer-verifier.ts`, `plugins/ghcr`, `plugins/scriptorium` and their tests. B owns `source-release-builds.ts`, `source-release-worker.ts`, Source HTTP client lifecycle and produced progression; worker composition edits are integrated by Sol. C owns Gateway/Admin, `packages/auth`, atomic DO admission/lifecycle and shared HTTP helper implementation proposal. D owns deployment/CI scripts and verification tests; shared inventory/manifests remain Sol-owned.
- Registry identity separates host, repository path, digest-addressed image reference, producer revision and resolver revision. The registry adapter receives only an allowlisted path belonging to its configured host; a fully qualified external identity must be parsed/checked before conversion. Signed statements retain canonical external identity. Wrong host/path/digest is rejected.
- Preserve the legacy resolver and add a revision-indexed registry of statically approved producer resolver bundles. Both selection and persistence choose the same exact producer revision. Signed Source evidence binds resolver identity/content; unknown, mismatched, tampered or unsigned resolver evidence fails closed. Never import/eval arbitrary Producer JavaScript in Control Plane or execute source scripts on the signing host. Bundles must retain upstream source provenance; adding an approved revision is not replacing a single hardcoded SHA.
- Source proof v2 keeps upstream BuildCatalog unchanged: statement `schemaVersion:2` adds signed `resolverDigest`; result adds strict `resolver:{producerRevision,resolverRevision,contractVersion,provenanceDigest}`. Resolver revision is SHA-256 of bundle bytes, producer revision is the Git SHA. V1 is parsed explicitly for historical proofs and verified only against the legacy approved revision. Registry export: `createScriptoriumCatalogResolverRegistry().resolve(producerRevision,resolverRevision?)` returns `{resolver,persistenceForModules}`; the legacy wrappers remain available. Descriptor/provenance/content must match the statically approved entry before admission.
- Explicit Source retry mirrors canonical release retry: `POST /v1/operator/source-builds/:jobId/retry`, `expectedRevision`, `idempotencyKey`, plus revalidated immutable Source identity. Gateway re-fetches published Release and resolves tag/SHA; CP rejects changed identity with 409. A D1 batch couples guarded revision CAS, idempotency receipt and audit. Keep `(source_id, github_release_id)` unique and lease epoch monotonic. Reset the attempt budget only for authorized explicit retry of eligible failure. Stale worker/token/epoch never regain authority.
- Source and composition share lease/retry/failure classification rules, not a new state authority. Source states remain queued/building/produced/admitted/failed. Exhausted expired leases become bounded terminal failures. Produced reconciliation uses persisted eligibility/backoff and bounded terminal handling so poison rows cannot monopolize the first page. Heartbeat continues through slow result verification; HTTP/proof/lease budgets must be coherent and tested.
- Additive migration `0007_source_release_recovery.sql` adds `revision INTEGER NOT NULL DEFAULT 0 CHECK(revision>=0)`, `admission_attempt INTEGER NOT NULL DEFAULT 0 CHECK(admission_attempt>=0)`, nullable `next_attempt_at INTEGER` and a due index on `(state,next_attempt_at,created_at,job_id)`. Reuse existing idempotency/audit tables. CP internal retry carries NewJob immutable identity plus the two canonical retry fields; browser form carries only the two fields, and Gateway supplies revalidated identity from its server-side job/Release lookup.
- One web-standard streaming bounded JSON reader is extracted from existing canonical Admission into `packages/contracts/src/http.ts`, exported for both planes; `RequestTooLargeError` maps to 413, malformed/invalid UTF-8 JSON to 400. Agent C prepares helper/extraction; Sol wires Source routes after B integrates. Limits apply to actual streamed bytes, without trusting Content-Length.
- Session admission becomes one atomic per-user DO operation, with count and insertion inside the same critical transaction. Expiry/revocation/one-use consumption remains authoritative. Bounded TTL cleanup and bounded active indexing must handle existing records and revoke-all without resurrecting credentials. Redirect helpers reject control/normalization tricks and confirm parsed origin. Admin sections report their own endpoint/status/safe code; unavailable optional capabilities must not erase healthy sections.
- One canonical variable projection covers direct Wrangler and inventory modes, including Admin origin/IDs, Source registry, auth TTL and routes. Preflight checks migrations, required secrets and immutable rollout inputs before starting Source-enabled workers. Production application remains separately authorized.

## Verification and integration order

1. Before implementation, preserve deterministic failing-before reproductions for F01/F05/F06/F08/F09/F10 (or document direct reproduction limitations and equivalent executable evidence). Add positive/negative tests before fixes in each owned worktree. Record exact commands and results, not assertions based solely on source strings.
2. Integrate shared contracts/additive migration first; A and B can implement independently against fixed seams, C handles Gateway/auth and D CI/deploy tests. Reconcile Source retry/UI and resolver/admission interfaces through Sol; no competing state machines or arbitrary edits to another owner's branch.
3. Run component regressions, then build/test integrated candidate. Include malicious Git configuration, publication/tag mutation, wrong signer/key revocation, OCI byte mismatch, resolver mismatch, D1 contention/crash/expiry/idempotency/poison queues, slow networks, streamed body bounds, OAuth/Admin/MCP, cold start/stop/resume, writer exclusion, quiesce and rollback compatibility.
4. High-signal verification CI: frozen install/full check/schema/boundaries; security + isolated D1/DO and Source→canonical Admission→Canary→Stable transitions; real disposable Producer/BuildKit/OCI adapter solve and digest verification; Kubernetes admission and actual service image builds. Actions has no runtime release/operator deployment authority and publishes no production artifacts from verification. Synthetic states or fixtures are labeled as such.
5. Separate Luna reviewers inspect complete candidate read-only for security, state transitions, compatibility, performance, cleanup, provenance and unnecessary implementations before integration approval. Triage by root cause, batch corrections, then run final CI on integrated HEAD. Do not disable checks to turn CI green.
6. Commit a closure matrix in `docs/verification/` mapping every ID to commits/files/tests/results, exact CI SHA/run, independent review disposition, migration/preflight/rollback instructions and residual risks. Submit a normal PR; no merge eligibility until acceptance, independent review and full CI are satisfied.
