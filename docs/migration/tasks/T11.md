# T11 — Stable release discovery, canary and persisted rollout

This task adds the T11 application state machines and a D1 adapter proposal. It does not configure an external publication feed or apply a migration. The Control Plane composition root must provide the authenticated operator admission verifier, the existing Scriptorium composition service, a disposable canary runtime, the follower reader and the T03 fenced desired-update writer. A mutable registry tag is never a candidate: the admission operation accepts an immutable digest and the full strict `BuildCatalog`, then rechecks OCI reachability and Sigstore provenance before persistence.

## Scheduled work

`runScheduledT11` is a bounded callable scheduled entry point. Run it from the five-minute Worker cron. Each invocation scans one page (50 entries, persisted checkpoint CAS), advances at most two candidate promotion workflows, and advances at most 25 follower rollouts. Each state transition is saved before returning. A fresh invocation owner token prevents an overlapping Worker execution from sharing a release-work lease. The candidate workflow uses idempotency keys for the disposable canary build/runtime/cleanup and persists the latest verified health sample. Promotion requires a continuous ten-minute healthy window with observations no more than ten minutes apart, cleans up the canary, rechecks immutable registry/provenance evidence, and CASes the stable channel only when the candidate is still newer than the current stable version.

The discovery checkpoint walks the already-admitted release catalog. It does not guess a GHCR tag/listing convention or treat registry presence as approval. The release ingestion composition root can be an operator route or a trusted immutable catalog poller; it must use the separate operator authority and the T05 registry/provenance verifier. Candidate metadata contains the canonical producer `BuildCatalog` and `RuntimeMetadata`; both producer revisions must match. Because T05's Sigstore verifier binds the image digest but cannot prove arbitrary posted catalog fields or paths, admission also requires a producer metadata attestation provider that verifies the exact catalog and runtime metadata against immutable producer/image evidence. That provider fails closed until the producer publishes this material. A signature/evidence outage is retryable; malformed metadata, untrusted evidence, or a digest conflict is denied and audited.

The canary is an explicitly configured disposable repository binding with its own repository and instance identity, checked against the current T03 binding before each action. The application adapter uses `ConfigurationService.plan`, `InstanceService.requestDesiredState`, and `OperationService.getById`; it does not use Kubernetes credentials in the Control Plane. It composes the candidate as an exact pinned base with the canary's configured add-ons, then starts it through the ordinary operation path. Health observations must be fresh provisioner observations for the matching operation, actual image digest, runtime epoch and instance; persisted samples include provider observation and smoke-probe evidence IDs for startup, auth, UI/API/MCP and persistence. A stop request remains pending until the ordinary stop operation succeeds and a fresh complete writer census proves zero writers for the retired runtime epoch. That cleanup proof is persisted before promotion.

After promotion, follower fanout persists stable-policy snapshots by page. Each follower uses its current selected add-ons, resource profile and configured build-cache service to compose against the promoted base. A failed or incompatible composition leaves the existing desired/current artifact untouched and records a blocked rollout. Pinned followers are not planned; stopped stable followers are marked deferred and remain stopped. A configuration, generation, binding, authorization, runtime, cluster, policy or state change before dispatch clears the old composed build and refreshes the snapshot. The normal desired-update/operation path performs the final CAS.

## D1 schema proposal (review and order with T03; not a migration)

The timestamps named `*_at` below use Unix milliseconds except candidate `created_at`, which is the ISO-8601 timestamp already present in the immutable candidate JSON and used as a stable scan key. `audit_events` is the canonical T03 audit table. No production database was changed.

```sql
CREATE TABLE release_candidates (
  release_id TEXT PRIMARY KEY,
  image_digest TEXT NOT NULL UNIQUE,
  version TEXT NOT NULL,
  image_repository TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('candidate', 'available')),
  candidate_json TEXT NOT NULL CHECK (json_valid(candidate_json) AND length(candidate_json) <= 1048576),
  created_at TEXT NOT NULL
);
CREATE INDEX release_candidates_scan ON release_candidates(created_at, release_id);

CREATE TABLE stable_release_channels (
  channel_key TEXT PRIMARY KEY CHECK (channel_key = 'stable'),
  current_release_id TEXT NULL REFERENCES release_candidates(release_id),
  revision INTEGER NOT NULL CHECK (revision >= 0),
  updated_at INTEGER NOT NULL
);
INSERT INTO stable_release_channels(channel_key, current_release_id, revision, updated_at)
VALUES ('stable', NULL, 0, 0);

CREATE TABLE release_discovery_checkpoints (
  checkpoint_id TEXT PRIMARY KEY CHECK (checkpoint_id = 'stable'),
  cursor TEXT NULL,
  revision INTEGER NOT NULL CHECK (revision >= 0),
  updated_at INTEGER NOT NULL
);
INSERT INTO release_discovery_checkpoints(checkpoint_id, cursor, revision, updated_at)
VALUES ('stable', NULL, 0, 0);

CREATE TABLE release_candidate_workflows (
  release_id TEXT PRIMARY KEY REFERENCES release_candidates(release_id),
  state TEXT NOT NULL CHECK (state IN (
    'queued', 'canary_building', 'canary_starting', 'canary_observing',
    'canary_cleanup', 'promoting', 'promoted', 'rolling_out', 'complete',
    'blocked', 'rejected', 'superseded'
  )),
  revision INTEGER NOT NULL CHECK (revision >= 0),
  attempts INTEGER NOT NULL CHECK (attempts >= 0),
  next_attempt_at INTEGER NULL,
  lease_owner TEXT NULL,
  lease_epoch INTEGER NOT NULL CHECK (lease_epoch >= 0),
  lease_expires_at INTEGER NULL,
  canary_artifact_digest TEXT NULL,
  canary_build_key TEXT NULL,
  canary_runtime_id TEXT NULL,
  canary_operation_id TEXT NULL,
  healthy_since INTEGER NULL,
  last_healthy_at INTEGER NULL,
  last_health_evidence_json TEXT NULL CHECK (
    last_health_evidence_json IS NULL OR
    (json_valid(last_health_evidence_json) AND length(last_health_evidence_json) <= 8192)
  ),
  cleanup_evidence_json TEXT NULL CHECK (
    cleanup_evidence_json IS NULL OR
    (json_valid(cleanup_evidence_json) AND length(cleanup_evidence_json) <= 8192)
  ),
  follower_cursor TEXT NULL,
  follower_planning_complete INTEGER NOT NULL CHECK (follower_planning_complete IN (0, 1)),
  canary_cleanup_complete INTEGER NOT NULL CHECK (canary_cleanup_complete IN (0, 1)),
  cleanup_disposition TEXT NULL CHECK (cleanup_disposition IN ('promote', 'reject')),
  failure_code TEXT NULL,
  updated_at INTEGER NOT NULL,
  CHECK ((lease_owner IS NULL) = (lease_expires_at IS NULL))
);
CREATE INDEX release_candidate_work_due
  ON release_candidate_workflows(state, next_attempt_at, lease_expires_at, release_id);

CREATE TABLE stable_rollout_fanout (
  release_id TEXT PRIMARY KEY REFERENCES release_candidates(release_id),
  cursor TEXT NULL,
  revision INTEGER NOT NULL CHECK (revision >= 0),
  complete INTEGER NOT NULL CHECK (complete IN (0, 1)),
  last_input_cursor TEXT NULL,
  last_next_cursor TEXT NULL,
  last_page_hash TEXT NULL,
  updated_at INTEGER NOT NULL
);

CREATE TABLE stable_rollouts (
  rollout_id TEXT PRIMARY KEY,
  release_id TEXT NOT NULL REFERENCES release_candidates(release_id),
  instance_id TEXT NOT NULL REFERENCES logical_instances(instance_id),
  cluster_id TEXT NOT NULL,
  snapshot_json TEXT NOT NULL CHECK (json_valid(snapshot_json) AND length(snapshot_json) <= 65536),
  state TEXT NOT NULL CHECK (state IN (
    'pending', 'building', 'waiting_build', 'dispatch_pending', 'operation_pending',
    'complete', 'deferred_stopped', 'skipped_pinned', 'blocked', 'superseded'
  )),
  revision INTEGER NOT NULL CHECK (revision >= 0),
  build_key TEXT NULL,
  build_id TEXT NULL,
  artifact_digest TEXT NULL,
  deployment_revision_id TEXT NULL REFERENCES deployment_revisions(revision_id),
  operation_id TEXT NULL REFERENCES operations(operation_id),
  failure_code TEXT NULL,
  next_attempt_at INTEGER NULL,
  updated_at INTEGER NOT NULL,
  UNIQUE (release_id, instance_id),
  CHECK (state <> 'operation_pending' OR operation_id IS NOT NULL)
);
CREATE INDEX stable_rollouts_due ON stable_rollouts(state, next_attempt_at, updated_at, rollout_id);

CREATE TABLE cluster_rollout_leases (
  cluster_id TEXT PRIMARY KEY,
  rollout_id TEXT NOT NULL REFERENCES stable_rollouts(rollout_id),
  owner TEXT NOT NULL,
  lease_epoch INTEGER NOT NULL CHECK (lease_epoch >= 0),
  lease_expires_at INTEGER NOT NULL,
  active_operation_id TEXT NULL REFERENCES operations(operation_id),
  updated_at INTEGER NOT NULL
);
CREATE INDEX cluster_rollout_lease_due ON cluster_rollout_leases(lease_expires_at, cluster_id);
```

Stable channel promotion and its system audit event commit in one D1 batch. The two `dispatchUnderClusterLease` statements are passed to T03's D1 platform store. In one transaction it must spend the exact unexpired `(cluster, rollout, owner, lease epoch)` fence, persist the rollout's `operation_pending`/operation ID, CAS the current repository binding, authorization revision, desired generation/configuration and stable/running policy, then insert the ordinary update operation, desired revision and audit event. A failed check must roll back both T11 fence statements. The adapter must not call a non-transactional enqueue after claiming a cluster lock. A terminal operation observation updates the rollout and clears only the matching active operation fence; unknown/missing observations retain and renew the fence.

## Verification and limits

Application tests cover semantic-version ordering, immutable admission deduplication/conflict, D1 cursor and workflow recovery, canary gating/rejection/cleanup fencing, stable-channel CAS, follower build failure, pinned/stopped preservation, changed desired configuration, cluster fencing and operation recovery across store reconstruction. D1 adapter tests use SQLite-compatible execution of the actual T11 SQL, separate from the application state-machine tests. The production composition requires T05 registry/signature verification, T04 catalog normalization, the real build cache/provider, an explicitly configured disposable canary and T03's atomic desired-update writer. No live producer image, GHCR, Worker, D1, Kubernetes or Actions test is claimed here; T14 owns real producer/runtime acceptance.
