# Deployment and disposable infrastructure

T12 adds three separate layers. NixOS host modules configure the private K3s runtime host and the isolated BuildKit host. Flux owns only static controllers and the shared platform overlay. The explicit Kind inventory and scripts provide a disposable local path for planning, preflight, and reviewable application. No file contains an old host address, account ID, device path, secret value, or production context.

## Inventory and gates

`infrastructure/test/disposable-inventory.json` is the local test input. It is validated by `infrastructure/scripts/inventory.mjs` and its strict schema at `infrastructure/schemas/deployment-inventory.schema.json`. It names a Kind cluster and derived context, local-only Control Plane D1 and Gateway KV identifiers, domain and GitHub App locators, public builder keys and bounded build/runtime policy, secret locators, immutable image digests, and an mTLS BuildKit endpoint with worker client CIDRs. Secret values are supplied by the owning environment outside this repository.

The checked-in inventory deliberately leaves image digests, the HTTPS Control Plane URL, BuildKit endpoint and repositories, worker CIDRs, the HTTPS Gateway origin and Pod-reachable Gateway URL, Gateway owner/App/OAuth identifiers, Build Worker signing ID and Ed25519 public key, build target platform, and ACME contact unavailable. Its optional T11 release policy is also deliberately unconfigured: it contains no canary owner, repository/instance binding, module selection, resource profile, operator actor, or signer identity. The validator reports missing canonical inputs as blockers. Replace them only with resources owned by the disposable environment; infrastructure `apply` rejects blockers, placeholder strings, remote Cloudflare mode, and any environment other than `disposable-test`. Worker `preflight` reports the same canonical-input blockers; `apply-local` remains limited to explicit local D1 migrations. The test inventory is not a production inventory or producer-acceptance fixture.

Before infrastructure application, create the referenced service credentials out of band in their listed namespaces. Use `Opaque` Secrets for the provisioner credential, Instance Access service auth, Build Worker control-plane token, Build Worker Ed25519 private key, BuildKit input/output Docker config (`config.json`), and Build Worker registry-read credential (`credential.json` containing strict `{"username":"…","password":"…"}` JSON). Those two registry files are separate: the Docker config is read by BuildKit and the simple credential file is read by the Node Build Worker. Use a `kubernetes.io/tls` Secret for BuildKit's client CA/certificate/key and a `kubernetes.io/dockerconfigjson` pull Secret with `.dockerconfigjson` in each workload namespace (`praetorium-system`, `praetorium-build`, and `praetorium-observability`). The Provisioner and Build Worker read their control-plane credentials from mounted files. The K8s apply preflight checks only each Secret's type and data-key names; it does not print or persist secret data. The Control Plane's `REGISTRY_PULL_CREDENTIAL` is a separate Cloudflare Worker secret with strict JSON `{"username":"…","password":"…"}` for OCI admission reads; it is not either Kubernetes registry credential. Secret provisioning is deliberately not automated here.

The T14 harness consumes the separate `infrastructure/test/acceptance-inventory.json`. It follows the exact seven-category owned inventory schema and currently marks every category missing. Its owner identity is explicitly unresolved. `scripts/preflight-integration.mjs` reads that file without consulting the current Kubernetes context, never executes resource-provided commands, and reports missing resources as `BLOCKED` / `NOT_CHECKED`.

## Explicit system network destinations

`network.kubernetesApiEndpoints` must list operator-verified API destinations as `{ "address": "<single IP>", "port": <TCP port> }`: the Kubernetes Service VIP and any backend address/port required by the selected CNI's Service-DNAT enforcement. It starts unset. Do not copy a host's API address or guess a Kind subnet. `network.controlPlaneCidrs` and `network.gatewayServiceCidrs` accept only explicit host `/32` or `/128` destinations for the corresponding Pod-reachable origin. Private/local origins, HTTP Gateway URLs and nonstandard ports require explicit entries; literal origin IPs must match the supplied destinations. Ports come from the configured URL, including the supported disposable HTTP Gateway port. Normal public HTTPS on 443 uses the reviewed public egress rule. No DNS-resolution or CNI matching success is inferred from an inventory value.

The renderer expands these public locators into static system NetworkPolicy rules. No broad CIDR, loopback, link-local, metadata endpoint or multicast destination can be added through these fields; additive rules must not reopen the public rule's metadata exclusions. Provisioner runtime egress uses named destination port `http` to owned Scriptorium Pods, paired with the tenant's exact declared-port ingress rule. The Instance Access service has no tenant egress. Source templates contain comment sentinels; full rendered manifests must contain structured rules and no unresolved tokens before apply. Validate API VIP/backend matching, DNS, named ports, permitted origins and denied metadata/private access against the explicitly owned disposable cluster and its policy-enforcing CNI. The checked-in Kind configuration does not establish that CNI acceptance.

## Disposable Kind flow

Run all commands from the repository root. `plan` and `preflight` do not mutate a cluster. Every command names its inventory explicitly:

```sh
node scripts/deploy-infrastructure.mjs plan --inventory infrastructure/test/disposable-inventory.json
node scripts/deploy-infrastructure.mjs preflight --inventory infrastructure/test/disposable-inventory.json
node scripts/deploy-infrastructure.mjs render --inventory /absolute/path/to/complete-owned-inventory.json
node scripts/deploy-infrastructure.mjs create --inventory infrastructure/test/disposable-inventory.json --confirm praetorium-t12-local
```

`render` writes the complete static YAML bundle using the same assembly function as `apply`, checks all placeholders and dynamic-namespace exclusions, and makes no cluster call or secret read. It requires a complete inventory; synthetic render tests do not establish that its image locators exist or satisfy producer acceptance.

`create` creates only the Kind cluster named by that inventory and labels its control-plane node with the inventory cluster ID and `praetorium.io/disposable=true`. It uses a separate owner-only kubeconfig under `/tmp/praetorium-t12-<uid>/<cluster-name>.yaml`, refuses to overwrite an existing inventory kubeconfig, and never reads or writes the operator's configured kubeconfig or current context. The subsequent `apply` uses that explicit file plus the derived context and rechecks every node's ownership labels before contacting the API server.

After `create`, bootstrap the namespaces required for operator-managed credentials using only that explicit kubeconfig and context:

```sh
kubectl --kubeconfig "/tmp/praetorium-t12-$(id -u)/praetorium-t12-local.yaml" --context kind-praetorium-t12-local create namespace praetorium-system
kubectl --kubeconfig "/tmp/praetorium-t12-$(id -u)/praetorium-t12-local.yaml" --context kind-praetorium-t12-local create namespace praetorium-build
kubectl --kubeconfig "/tmp/praetorium-t12-$(id -u)/praetorium-t12-local.yaml" --context kind-praetorium-t12-local create namespace praetorium-observability
```

Then provision the listed Secrets out of band. The deployment-only Cloudflare DNS token reference belongs in the cert-manager namespace when using the deployment overlay.

Bootstrap Flux against the explicit disposable context and configure its `flux-system` Git source to the reviewed, sanitized repository revision. Flux's controller Kustomization installs pinned Traefik and cert-manager Helm releases. The platform Kustomization is suspended in this template; keep it suspended until the inventory has real inputs and a rendered platform overlay has been reviewed. Then run:

```sh
node scripts/deploy-infrastructure.mjs apply --inventory infrastructure/test/disposable-inventory.json --confirm praetorium-t12-local
```

Application requires exact Kind v0.31.0, `kubectl`, a successful render of the base, controller, deployment and disposable Kustomize targets, the cert-manager and Traefik CRDs, ready immutable service images, all BuildKit mTLS inputs, and the namespace-local operator-managed Secrets above. It requires v1 admission API discovery, server-dry-runs the complete rendered `overlays/disposable` bundle with strict validation, applies its 14 admission guards, waits for current-generation type-check status and exact Deny bindings, then applies the complete static bundle and checks the four fixed deployments, and rejects unresolved tokens or any `praetorium-instances-*` namespace. It never invokes Flux prune or applies dynamic instance resources. The static Provisioner ServiceAccount has the minimal bootstrap ClusterRoleBinding; it binds per-tenant permissions only after namespace ownership validation. The Node Provisioner currently stays unready and claims no operation because Scriptorium's S03 assignment ABI and S02 grant-probe transport are unavailable. Runtime namespace/workload/RBAC creation remains gated until those production ports and permissions are implemented and reviewed.

The deployment script resolves tools from `PATH`, or from explicit executable paths in `PRAETORIUM_KIND_BIN`, `PRAETORIUM_KUBECTL_BIN`, and `PRAETORIUM_KUSTOMIZE_BIN`. When standalone Kustomize is absent, it validates and renders the four checked-in targets with `kubectl kustomize`. The preflight performs only client-version and local-render checks; it does not inspect or contact the current Kubernetes context.

For local ingress verification, use an explicit context and forward the Traefik service without opening a host port:

```sh
kubectl --kubeconfig "/tmp/praetorium-t12-$(id -u)/praetorium-t12-local.yaml" --context kind-praetorium-t12-local -n traefik port-forward service/traefik 8443:443
```

Use an instance hostname beneath `instanceHostnameSuffix` and the self-signed certificate issued by the disposable overlay. The port-forward process is local to the operator; it does not change the cluster's public ingress policy.

When the disposable cluster is no longer needed, remove only the explicitly named Kind cluster after checking the recorded inventory and preserving any evidence required by the campaign:

```sh
kind delete cluster --name praetorium-t12-local --kubeconfig "/tmp/praetorium-t12-$(id -u)/praetorium-t12-local.yaml"
```

Do not substitute an operator's current Kubernetes context or a deployment cluster for this test inventory.

## Local Workers and D1

`infrastructure/workers/*.template.json` declare the current bindings and public variables. Both use the pinned `2026-07-30` Workers compatibility date. Control Plane owns the single `CONTROL_PLANE_DB` binding to `praetorium-platform` and `REPOSITORY_COORDINATOR`, with four SQL migrations in `apps/control-plane/migrations`. Its `GATEWAY_SERVICE` binding targets `praetorium-gateway`; Gateway has no D1 database, and its `CONTROL_PLANE` binding continues to target `praetorium-control-plane`. `USER_AUTH_STATE` and `EPHEMERAL_CODES` are Gateway auth stores, and `GATEWAY_KV` stores bounded indexes/rate limits and the public signing-key registry.

The Gateway variables are `GATEWAY_ORIGIN`, `CONTROL_PLANE_ORIGIN`, its session/handoff/access-grant TTLs, `GATEWAY_INSTANCE_HOSTNAME_SUFFIX`, `GATEWAY_ALLOWED_REPOSITORY_OWNER`, `GITHUB_APP_ID`, `GITHUB_OAUTH_CLIENT_ID`, and `GATEWAY_TOKEN_ENCRYPTION_KEY_ID`. Both origins are exact HTTPS origins. `CONTROL_PLANE_ORIGIN` is the trusted runtime-identity issuer and comes from the same `domains.controlPlaneUrl` inventory value used by Control Plane. `CONTROL_PLANE_GATEWAY_AUTH` is the same shared secret on Gateway and Control Plane. Gateway also requires `GITHUB_OAUTH_CLIENT_SECRET`, `GATEWAY_GITHUB_WEBHOOK_SECRET`, the GitHub App PEM in `GITHUB_APP_PRIVATE_KEY`, `INSTANCE_ACCESS_SERVICE_AUTH_TOKEN`, the three digest peppers, `GATEWAY_TOKEN_ENCRYPTION_KEY`, and `GATEWAY_SIGNING_KEY`. Keep the webhook secret, App private key, OAuth client secret, and Gateway signing key as separate secrets. `GATEWAY_SIGNING_KEY` is JSON containing a private P-256 JWK and key ID. The KV namespace must contain the matching active public key record before Gateway serves requests.

Control Plane's `BUILD_POLICY_JSON` is generated from the explicit inventory when its output repository, target platform, public builder keys, runtime limits, and all cache-retention controls are supplied. It must match the strict `apps/control-plane/src/build-composition.ts` policy: HTTPS registry origin, repository allowlist and output repository, image and request limits, target platform, Ed25519 builder public keys, runtime resource limits, and `cacheRetention`. The retention block requires operator values for `maxBytes` (safe integer ≥ 0), `maxEntries` (safe integer ≥ 1), `minAgeMs` (safe integer ≥ 0), and `maxEvictions` (integer 1–32). The checked-in disposable inventory leaves all four null; validation reports each as a blocker and the Worker plan/preflight omits `BUILD_POLICY_JSON` until all four are supplied. Do not fill them with guessed production limits. Retention planning is advisory and pin-aware; these controls do not authorize an OCI deletion executor or support a reclaimed-storage claim. The output repository is the only repository in the generated admission allowlist. `BUILD_WORKER_ID` is derived from the explicit cluster ID. `BUILD_WORKER_AUTH_TOKEN` enables build routes only when the policy is configured, and matches the Build Worker's mounted service token. `REGISTRY_PULL_CREDENTIAL` is an optional, separate registry read credential. `CONTROL_PLANE_ORIGIN` on both Workers comes only from `domains.controlPlaneUrl` and must be the exact trusted HTTPS origin, with no credentials, path, query, or fragment. `GATEWAY_ORIGIN`, `INSTANCE_HOST_SUFFIX`, and `RUNTIME_REGISTRY_HOST` are runtime-policy inputs; the checked-in T12 inventory leaves its missing origins blocked.

Control Plane requires `RUNTIME_IDENTITY_SIGNING_KEY`, a separate JSON secret shaped as `{ "kid": "…", "privateKeyJwk": { … } }` for runtime identity credentials. `RUNTIME_CONTROL_SIGNING_KEY` is a distinct private P-256 JWK for optional short-lived runtime-control credentials. Keep both separate from one another, Gateway's `GATEWAY_SIGNING_KEY`, Build Worker's Ed25519 signing key, and GitHub's App PEM.

The Control Plane template runs its scheduled handler every five minutes (`*/5 * * * *`). `RELEASE_POLICY_JSON` is optional public policy generated only from a complete operator-owned inventory entry. Its strict shape has a release `workerId`, the inventory's `clusterId`, `operatorActorId`, a non-empty Sigstore `signerIdentityAllowlist`, and a canary with `owner`, `disposable: true`, `production: false`, numeric repository ID, exact instance ID, binding epoch, authorization revision, requested modules, and resource profile ID. The checked-in inventory does not enable this policy and supplies no made-up canary identity. When enabled, `RELEASE_OPERATOR_TOKEN` must be a 32–4096 character non-space printable ASCII secret, distinct from `CONTROL_PLANE_GATEWAY_AUTH`, `BUILD_WORKER_AUTH_TOKEN`, and `PROVISIONER_AUTH_TOKEN`.

Credential retirement uses the separate `RUNTIME_CREDENTIAL_RETIREMENT_AUTH` secret on both Control Plane and Gateway. Provision the same 32–4096 character non-space printable ASCII value on those two Workers; keep it distinct from `CONTROL_PLANE_GATEWAY_AUTH`, `PROVISIONER_AUTH_TOKEN`, `BUILD_WORKER_AUTH_TOKEN`, and `RELEASE_OPERATOR_TOKEN`. It is not a Node Provisioner credential. The Worker planner and preflight report this requirement and never inspect secret values.

The Control Plane D1 registry tracks known runtime Git credentials by repository, instance, runtime epoch, lease, permission, expiry, and status. It stores Gateway-encrypted credential blobs, never plaintext GitHub bearer tokens. After the fenced old-runtime quiescing checkpoint, Control Plane marks matching known records `revocation_pending` and calls Gateway through `GATEWAY_SERVICE`. Gateway's provider treats GitHub's `204` revoke response as the retirement barrier and updates the authoritative record state; Control Plane checks that no matching unexpired record remains pending before lifecycle processing continues. A provider `401`, rate limit, network failure, or request deadline leaves the barrier closed for retry or until the credential's recorded expiry has passed. Expiry of a lease alone is not evidence that the old runtime can no longer write; writer-absence proof still depends on the separate runtime quiesce/recovery contract.

The release admission and promotion gates remain blocked even after policy configuration: S01 has not supplied its immutable producer metadata attestation ABI, and authenticated S02/S05 UI, API, MCP, and persistence conformance observations are unavailable. The Control Plane does not substitute an OCI digest, ready Pod, or caller-provided catalog for those producer-owned proofs. Do not set the optional `PROVISIONER_AUTH_TOKEN` route while the actual producer assignment and grant-probe ports are unavailable. Its eventual policy also requires `PROVISIONER_WORKER_ID`, `PROVISIONER_CLUSTER_ID`, the Gateway and Control Plane origins, `INSTANCE_HOST_SUFFIX`, `RUNTIME_REGISTRY_HOST`, and `GIT_CREDENTIAL_BROKER_LOCATOR`. The Worker plan and preflight report names and public policy metadata only; they do not read, print, or verify secret values and make no remote Cloudflare calls. Secret provisioning and remote Worker/D1/KV provisioning remain separate operations.

```sh
node scripts/deploy-workers.mjs plan --inventory infrastructure/test/disposable-inventory.json
node scripts/deploy-workers.mjs preflight --inventory infrastructure/test/disposable-inventory.json
node scripts/deploy-workers.mjs apply-local --inventory infrastructure/test/disposable-inventory.json --confirm praetorium-t12-local
```

`apply-local` applies only these Control Plane Wrangler D1 migrations with `--local` and a persistence path under `/tmp/praetorium-t12-workers/<cluster-name>`: `0001_repository_platform.sql`, `0002_stable_release_rollouts.sql`, `0003_staged_configurations.sql`, and `0004_runtime_git_credentials.sql`. It targets the `praetorium-platform` database declared in the Control Plane template. Gateway's Durable Objects and KV are binding declarations only here; this command does not start a Worker emulator, provision or modify Gateway storage, or run a Gateway D1 migration. The script refuses remote Cloudflare mode and requires the confirmation string to match the explicitly owned disposable cluster name. It does not deploy a Worker or use account credentials. Remove that directory when the disposable inventory expires. Remote Worker/D1/KV provisioning and secret provisioning remain separate, authorized operations.

The Node Provisioner receives the actual `PROVISIONER_*` names, including the HTTPS Control Plane URL, cluster/worker identity, runtime service locations, maximum CPU/memory/ephemeral-storage values and capacity age. `PROVISIONER_CREDENTIAL_PATH` is `/var/run/secrets/control-plane/credential`, matching the read-only Secret mount. The runtime limits come from `buildPolicy.runtimeResourceLimits`, so the Control Plane's build policy and Provisioner use the same caps. The Provisioner startup wires the actual operation client but currently supplies unavailable S03 runtime-assignment and S02 grant-probe transports; `/readyz` stays 503 and no operation is claimed.

T07 owns each dynamic tenant NetworkPolicy. Its generated tenant Pod has `arcadia.io/platform=arcadia-platform` and `app.kubernetes.io/name=scriptorium`. The policy admits only the configured Traefik namespace with `app.kubernetes.io/name=traefik`, the configured Instance Access namespace and service label, and `praetorium-system` with `app.kubernetes.io/name=provisioner`; each ingress rule is limited to the producer-declared application HTTP port. T07 also owns the tenant egress rules. The static T12 overlay does not add a separate broad egress policy or change production defaults.

The Node Build Worker receives the application's `PRAETORIUM_*` variables and reads its service token, private Ed25519 signing key, BuildKit mTLS files, BuildKit Docker config and separate simple registry-read credential from mounted Secrets. Its registry origin and image/request limits come from the same inventory policy as Control Plane, with limits validated against both workers' accepted ranges. The inventory supplies the matching public signer key to `BUILD_POLICY_JSON`; its `keyId` must match `buildWorker.signingKeyId`. The Control Plane's registry pull secret, BuildKit input/output Docker auth, Build Worker's registry-read credential, application image-pull credential, Gateway secrets and runtime-control private key are separate credential surfaces. The worker uses the inventory's HTTPS Control Plane origin, GHCR origin, composition/frontend/output repository locators and absolute `buildctl` path. The Node Instance Access adapter receives `GATEWAY_URL`, `GATEWAY_ORIGIN`, `INSTANCE_ACCESS_INSTANCE_HOSTNAME_SUFFIX`, and `INSTANCE_ACCESS_SERVICE_AUTH_TOKEN`. `gatewayServiceUrl` must be reachable from its Pod; the checked-in disposable inventory leaves it missing. Only the disposable overlay sets `NODE_ENV=test` for the local HTTP Gateway URL allowed by that adapter.

The Build Worker init container runs the same immutable image as UID/GID 10001 and executes `node dist/prepare-runtime-secrets.js`. Only this init sees the five read-only projected Secret volumes. It copies the fixed files into UID-owned `0700` directories and `0600` regular files below `/var/run/praetorium-build-worker/private`, backed by an 8 MiB memory emptyDir. The application mounts that volume read-only; its existing strict file validators remain enabled. A separate 2 GiB emptyDir provides the prepared private build scratch directory at `/tmp/praetorium-build-worker/private`. No credential is copied during image construction. These are init-time snapshots: updating a Secret requires recreating the Pod to prepare new copies; no automatic key rotation is performed.

## NixOS roles and BuildKit isolation

`infrastructure/nixos/flake.nix` exports `runtimeHost` and `buildHost` modules. A deployment host must compose one role with its reviewed hardware, boot, network, and operator inventory. No old hardware configuration or device UUID is copied here.

`infrastructure/docker/service-runtime.Dockerfile` keeps compilation and production runtime in separate stages. Its caller must pass immutable `NODE_BUILD_IMAGE` and `NODE_RUNTIME_IMAGE` references plus the workspace `SERVICE_PACKAGE`; the Dockerfile-specific ignore file excludes Git data, dependency trees, environment files, secrets, and generated outputs from the build context. The runtime stage does not include a Docker socket or copy registry credentials into the image. Use this generic recipe for Provisioner and Instance Access; Instance Access uses the deployed `node dist/server.js` command override.

The Build Worker uses `infrastructure/docker/build-worker.Dockerfile`, which additionally copies the client executable from an operator-approved digest-pinned `BUILDKIT_CLIENT_IMAGE`. Set `BUILDKIT_CLIENT_BUILDCTL_PATH` to the observed source path in that image. Read `buildWorker.buildctlPath` once from the selected owned inventory and pass that exact value as the Dockerfile build argument `PRAETORIUM_BUILDKIT_BUILDCTL_PATH`; the recipe uses it for the copy destination, image environment and executable check. The same inventory field renders the Kubernetes ConfigMap. A separately typed destination path would break that binding. A null field in the checked-in draft is still a blocker; the local component-build inventory does not make the full deployment inventory ready. The client image, Node base images and service output must use immutable digests; use the owned registry for disposable verification.

The runtime role keeps SSH and the Kubernetes API closed except to explicit management CIDRs, disables bundled K3s Traefik, and leaves public ingress stopped by default. If public HTTP ingress is enabled in a reviewed deployment inventory, Traefik permanently redirects its web entrypoint to HTTPS. Its K3s datastore stays under `/var/lib/rancher/k3s`; an optional etcd snapshot directory must be separate.

The BuildKit role belongs on a separate host. It requires worker-only IPv4 source CIDRs, explicit registry/input egress CIDRs through a credential-free proxy, runtime mTLS certificate references, an operator-provisioned XFS mount with a hard project quota, and fixed systemd CPU, memory, and task limits. A root-owned preparation unit applies the XFS project hard limit and gives the dedicated state directory to the service user. RootlessKit creates a slirp4netns namespace, loopback access to the host is disabled, and systemd exposes only the TAP device required by slirp4netns. The daemon runs as the non-root `buildkit` user, and BuildKit parallelism is fixed to one. K3s, Docker, Kubernetes credentials, GitHub tokens, and runtime credentials are forbidden on this host.

Supply the BuildKit mTLS server key/certificate/client CA through the host's secret mechanism and provision the XFS device before enabling the role. The module never formats a device. Host deployment itself is not performed by the T12 scripts.

## Stable stopped-instance routing

Traefik watches the dynamic tenant namespaces with cluster-scoped CRD RBAC. The static fallback sends matching stopped-instance hosts to `instance-access` at priority1; a running instance has an exact-host route at priority10, while `/_platform` always wins at priority1000. That service remains available while an instance is stopped, so its provider can return the durable stopped response without an instance workload or dynamic Flux object. The disposable overlay uses a self-signed wildcard certificate. The deployment overlay uses cert-manager DNS-01 with a Kubernetes secret reference to the Cloudflare token; the token itself is never stored here.

## Verification limits

Nix syntax and schema validation show that templates parse and reject incomplete input; they do not certify a live K3s, Flux, Worker, D1, ingress, registry, or BuildKit deployment. The checked-in inventory intentionally cannot pass infrastructure application or Worker preflight until an operator supplies owned disposable test resources, real Gateway/Control Plane locators, a public builder key and target platform, and immutable service image digests. Production DNS, Cloudflare, D1, NixOS, and K3s changes remain outside this task.

The admission status gate does not prove the admission plugin is enforcing, and
Kubernetes does not fully type-check CRD expressions. Run actual positive/negative
admission and packet probes in the explicit owned disposable cluster before
claiming readiness. Kind's pinned NetworkPolicy controller is policy-capable but
fail-open; configuration alone is insufficient. See
[admission apply](../verification/ADMISSION-APPLY.md),
[Kind runtime](../verification/KIND-RUNTIME.md), and
[Traefik watch](../verification/TRAEFIK-RUNTIME-WATCH.md).
