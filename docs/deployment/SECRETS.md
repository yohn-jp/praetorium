# Hosted secret registration and stewardship

This describes the file-backed Kubernetes inputs and Cloudflare Worker secret handling used by the existing deployment scripts. It does not introduce another secret platform. The scripts keep file contents out of Git, generated Worker configuration, and routine command output. Reuse an existing credential only after its source and matching consumer state are verified. If an optional provider secret or credential source has not been inspected, record `NOT_CHECKED`; a manifest locator is not evidence that the value exists.

## Initial issuance, registration, and lifecycle

1. Inspect the exact target provider resource before treating a role as new. The owner confirmed the two Control Plane shared-auth secrets absent, but subsequently confirmed the Gateway shared-auth secret present. Targeted read-only Runtime checks found their three K3s Secrets absent. The Gateway candidate was initially excluded, then restored after explicit owner approval for the one-credential cutover. Its registration remains pending. DNS Secret and GHCR credential presence remain unconfirmed. The checked-in secret references describe names and consumers, not provisioned state. When an existing secret is present but its bytes cannot be recovered, keep the role `SOURCE_NOT_RECOVERED` and coordinate a deliberate cross-consumer recovery or rotation; never overwrite it with a newly generated value just to make a file manifest complete.
2. Place a verified file at its exact canonical path, owned by the deploying user, mode `0600`, under mode-`0700` parent directories. Copying a file must preserve bytes; do not normalize tokens by adding a newline. Keep an encrypted operator-controlled backup outside Git and record only its locator and state in metadata. The dated harness copies in `/data/praetorium-hosted-20261018` preserve provenance; they are not represented as an independent backup.
3. Complete `secret-files.json` only from real files. Do not add paths for missing roles and do not use placeholder data. Keep `secret-files.partial.json` marked non-deployable until all eleven inventory roles are present and local validation confirms every path and mode.
4. For the new notification roles, the two staged random values are initial inputs only. Register each exact file to both its Control Plane Worker secret and its matching Runtime K3s Secret in one coordinated deployment; keep them inactive until the end-to-end notification proof succeeds.
5. If read-only inspection confirms that no existing Build Worker signer/trust pair exists and build routes are being enabled, create one Ed25519 PKCS#8 PEM private key at the canonical file path with mode `0600`. Derive the matching 32-byte raw public key and encode those bytes as standard Base64 in the private inventory's `buildPolicy.builderKeys`; do not Base64-encode the SPKI/DER wrapper. Set a stable `buildWorker.signingKeyId` that matches the policy entry and Build Worker `PRAETORIUM_BUILD_SIGNING_KEY_ID`. Verify the private/public pair before registration. The Control Plane build policy and Worker signer must be deployed from the same reviewed inventory. If an existing active key or remote policy is found, recover and reconcile it instead of creating a second key.
6. If no suitable Cloudflare DNS token source exists, create a zone-restricted Cloudflare API token for `yohn.jp` with only `Zone:DNS:Edit` and `Zone:Zone:Read`, store its raw token bytes at the canonical path with mode `0600`, and register it only as `cert-manager/praetorium-dns-api-token` key `api-token`. This matches the [cert-manager Cloudflare DNS-01 token requirements](https://cert-manager.io/docs/configuration/acme/dns01/cloudflare/). Do not use a Tunnel token or Cloudflare account-management token for cert-manager.
7. If no approved GHCR credential source exists, use the existing organization-approved credential process to provision separate least-privilege read and write inputs for the configured packages: the Build Worker pull file is JSON with exactly `username` and `password`, and the BuildKit push file is a Docker config with `auths.ghcr.io.username` and `auths.ghcr.io.password`. Grant read-only package access for the configured composition/output packages to the pull identity and package write only for the output package to the push identity. GitHub documents Container Registry PAT classic auth with `read:packages` for pulls and `write:packages` for publishing ([GHCR authentication](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)); grant package access only to the necessary packages. The installed GitHub App's repository `Contents` permission and a local `gh` login without package scopes do not provide these GHCR credentials. The publisher workflow's job-scoped `GITHUB_TOKEN` can publish service images, but it is not available to the long-running Build VM. Do not create a new account or credential platform solely for this role.
8. After inventory, secrets, ingress, and owner authorization are ready, run `scripts/deploy-platform.mjs --check` from a clean immutable checkout. This preflights Cloudflare and K3s before mutation. `--apply` is a full registration/deployment operation: it creates missing Kubernetes Secrets from the files, refuses mismatched existing Secret contents rather than silently rotating them, updates mapped Cloudflare Worker secrets, deploys Workers, applies the declared D1 migration, and reconciles K3s/Traefik/cert-manager. It is not a secret-only command.
9. Mark a role `REGISTERED` only after the required surfaces were written from the same source file. Mark it `ACTIVE` only after consumers have rolled out and the applicable health, JWKS, certificate, and notification checks pass. A filename, Worker Secret name, Kubernetes Secret name, or successful local preflight alone is not activation evidence.
10. Mark a backup `VERIFIED` only after an independent protected copy was checked byte-for-byte. Record its locator and verification time, never values or hashes. The current staging state has no separate verified backup.
11. Recovery restores the exact registered bytes to the same consumers after the source file is validated. Rotation is a separate, explicit owner operation with a coordinated cutover across every consumer; no script in this workflow automatically rotates existing Cloudflare keys, service auth, BuildKit certificates, or GHCR credentials.

For Cloudflare registration, the existing [platform deployment script](../../scripts/deploy-platform.mjs) uses the pinned workspace Wrangler and sends mapped file contents through standard input to `wrangler secret put`; the value is not placed in generated JSON or routine output. For Kubernetes registration, [deploy-k3s](../../scripts/deploy-k3s.mjs) checks the inventory's exact Secret names, types, and data keys, then creates missing Secrets and refuses an implicit replacement. Keep these procedures together; do not manually update only one side of a shared credential.
