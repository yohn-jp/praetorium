# T06 — Build Service and worker

This task implements the worker-side BuildProvider and a Node worker entry that claims immutable build inputs from Control Plane over authenticated HTTP, runs only an approved producer frontend on a remote BuildKit service, and reports attempt-fenced results. The Control Plane remains the authority for build state and artifact admission; a worker success report is only a candidate until the registry verifier accepts its bytes and provenance.

## Security and execution boundary

- The BuildKit frontend is selected by an immutable approved digest. The proposed producer handoff invokes `gateway.v0` with `--opt source=<approved-frontend-repository>@<buildKitDigest>` and `--opt scriptorium.build-input.v1=<base64url(canonicalBuildInput)>`; the only output is `type=image,name=<operator-output-repository>:candidate-<buildKey>-<attemptHash>,push=true`. The repository values come from operator or T05 catalog configuration, not the claim. No local source is sent. This wire format is a consumer handoff requirement until Scriptorium publishes an approved frontend implementing it; it is not a claim that the inspected producer artifact supports arbitrary composition. The worker never accepts a Dockerfile, shell command, repository URL, branch, or caller-selected output registry.
- The canonical BuildInput is bounded and passed only as a base64url gateway option; no local build context is created. The work repository and GitHub installation credential are not available to the worker or BuildKit session. BuildKit's auth session uses a separate operator registry credential for approved input/output registries; that credential is not mounted into recipe execution.
- BuildKit is remote and configured through mTLS. The worker is a Node process with a separate Control Plane service credential; it does not load Kubernetes configuration or runtime credentials. Registry push authentication is separate from Control Plane authentication and is not passed as a build argument, local context file, or BuildKit `--secret`/`--ssh` mount.
- The worker allows one claimed solve at a time, bounds the BuildKit process deadline, progress bytes, response bodies, generated context, and child environment. Lease heartbeats carry monotonic attempt progress and cancellation state. A stale/lost lease cancels the remote solve, and late reports cannot admit an artifact.
- Candidate image tags are unique to the build key and attempt. Cancellation sends `SIGTERM` to `buildctl` and escalates to `SIGKILL` after three seconds; local temporary state is removed on every exit. The remote host must verify that disconnected attempts stop promptly and enforce storage quotas. Candidate tags left by failed or canceled exports need an operator-owned registry retention policy; this worker has no delete permission or tag-deletion path.
- The executable Node entry claims, heartbeats, and reports through the canonical `/internal/builds/*` HTTPS routes using a private worker service-token file. The attempt lease token is sent only to Control Plane. The worker signs only the statement returned by `GhcrCandidateVerifier` after immutable image and composition bytes have been checked; its Ed25519 PKCS#8 key is loaded from an owner-only file and is never sent to BuildKit or Control Plane.
- `PRAETORIUM_BUILD_REGISTRY_URL` defaults to `https://ghcr.io` and may name an operator-configured HTTPS registry. HTTP is accepted only for exact `127.0.0.1:<port>` when `PRAETORIUM_BUILD_ALLOW_INSECURE_LOOPBACK_REGISTRY=1` is explicitly set for disposable local acceptance. The configured origin must match the fixed output repository; registry requests reject redirects, and no origin or credential comes from a build claim. `PRAETORIUM_BUILD_COMPOSITION_REPOSITORY` and the registry origin bound registry reads. `PRAETORIUM_BUILD_MAX_IMAGE_LAYER_BYTES`, `PRAETORIUM_BUILD_MAX_IMAGE_VERIFICATION_MS`, and `PRAETORIUM_BUILD_MAX_REGISTRY_REQUEST_MS` are required operator budgets for image bytes, total image verification time, and each registry request; the worker does not select defaults. The attempt signal reaches registry requests and the inspector smoke so cancellation stops verification as well as BuildKit. A separate optional `PRAETORIUM_BUILD_REGISTRY_PULL_CREDENTIAL_FILE` holds only the registry read credential. BuildKit's Docker auth file remains a separate push/build-input credential surface.
- The remote BuildKit service still needs an operator-owned resource envelope, rootless execution, bounded storage, concurrency limit, and network egress policy. The Node worker cannot enforce cgroup, storage quota, or network namespace limits on a remote daemon; the configured host must enforce them before a live build is certified.

## Producer and inspection gates

There is no approved `BuildCandidateReceiptReader` for the currently pinned producer. The reader contract is intentionally narrow: it must declare support for the exact immutable `BuildInput` before a solve starts and, after the solve, return the digest-addressed composition-manifest repository and digest from a documented producer receipt. The worker does not guess an OCI annotation, exporter metadata key, referrer convention, or tag. With no reader installed, the provider reports non-retryable `BUILD_FAILED` before invoking BuildKit.

The pinned source snapshot `c90e95d` builds through its root `Dockerfile` and `scripts/profile-package.mjs`; its documented OCI path is `docker build`. It does not implement the `gateway.v0` options or composition-manifest receipt required by this worker. The adapter therefore remains intentionally unavailable for that producer until its build handoff is implemented and reviewed.

The executable currently wires `GhcrCandidateVerifier` to `UnavailableCompositionArtifactInspector`, which always rejects. No digest-backed filesystem/module-closure scanner or declared health-smoke runner exists in this task environment. Even after the producer receipt contract is implemented, a candidate cannot be signed until an inspector reads the immutable image, compares both server and browser closures and native dependencies, and runs the composition's declared smoke. The Control Plane independently checks the signature and report bindings before admission.

BuildKit documents rootless mode as running the daemon as a non-root user and notes that rootless networking uses the host mode unless RootlessKit supplies an isolated network namespace. The remote host therefore needs both verified rootless/user-namespace support and an egress-restricted network setup; a TLS endpoint alone does not establish either property. See [BuildKit rootless mode](https://github.com/moby/buildkit/blob/master/docs/rootless.md) and [BuildKit daemon configuration](https://github.com/moby/buildkit/blob/master/docs/buildkitd.toml.md).

## Verification evidence

The source campaign's `infrastructure/nixos/modules/container-build.nix` enables a local Docker socket, gives a self-hosted GitHub Actions runner access to it, and asserts only that the VM is separate from the K3s host. It does not configure the accepted rootless remote BuildKit service and is not reused by T06.

At the T06 implementation environment check, `buildctl`, `buildkitd`, and `docker` were absent; no `BUILDKIT_HOST` or `DOCKER_HOST` endpoint was configured, and no local BuildKit or Docker socket existed. No live BuildKit solve, registry round-trip, runtime deployment, or production/Actions/public-registry operation was performed. Rootless daemon identity, user-namespace support, CPU/memory/disk quotas, network isolation/egress, registry capability, and real producer S01 closure remain **NOT_CHECKED** until an explicitly owned disposable build host and registry are available.

## Acceptance

Local verification exercises the executable worker composition, HTTPS queue adapter, fixed BuildKit command adapter, file-key signer, registry verifier ports, and fail-closed producer/inspection gates. It covers strict immutable-input validation, fixed frontend/args, mTLS flag construction, bounded progress, deadline and abort cleanup, lease loss/cancellation, stale report rejection, one-attempt result binding, and absence of repository/runtime credentials from child environment and build context.

The live acceptance gate is a rootless remote BuildKit solve plus disposable registry push/pull and Control Plane admission against the actual Scriptorium Runtime Base/Build Kit. It must confirm server/browser closure and producer metadata against OCI bytes. Fixture-only/local tests do not satisfy this gate. Current-app replacement is built before the old runtime is drained.
